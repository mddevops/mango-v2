## 1. Текущее состояние V2

### 1.1. Готово (только настройки)

- **[факт V2] Подключение Mango VPBX** — `integration_connections` (`provider = mango_vpbx`): название (уникально
  в пределах провайдера), активность, `verification_status` (всегда `unverified`), `secrets` — `api_key` и
  `api_salt` в одном поле с cast `encrypted:array`, скрыты из сериализации и аудита (`IntegrationConnection`,
  `IntegrationProvider::secretFields`). Управление — только полный администратор (`connections.manage`,
  `connections.secrets`).
- **[факт V2] Салоны подключения** — `integration_connection_showroom` (хотя бы один салон).
- **[факт V2] Привязка источника** — `integration_connection_sources`: не больше одной привязки на источник и
  провайдера; источник можно привязать только к подключению, разрешённому для его салона.
- **[факт V2] Линии** — `integration_lines`: `type` = `phone` | `sip`, исходное `value` и `match_key`; уникальность
  `(integration_connection_id, type, match_key)`, составной FK на привязку. `IntegrationLine::matchKey`: телефон —
  только цифры (`8XXXXXXXXXX` и 10 цифр → `7…`), SIP — `mb_strtolower(trim())`, без разбора префикса `sip:`.
- **[факт V2] Канал «Прямой звонок»** — `contact_channels.code = direct-call` (сидер). Допустимость канала для
  источника хранится в `source_channel` и проверяется сервером.
- **[факт V2] Телефоны** — `App\Support\Phone::normalize`: только полный российский номер `7XXXXXXXXXX` (8/+7/7);
  остальное (короткие, SIP, иностранные) → `null`. Основной номер заявки — `orders.phone` (NOT NULL, индекс),
  дополнительные — `order_phones`; клиент — `clients` / `client_phones` (номер уникален во всей базе).
- **[факт V2] Заявки** — `OrderManager`: ручное создание, `createFromSiteRequest` (блокировка обращения, поиск или
  создание клиента, счётчик повторов, создание заявки и аудит в одной транзакции, повтор при нарушении индексов
  `client_phones_phone_unique` и `orders_client_showroom_repeat_unique`). Происхождение `OrderOrigin`: `manual`,
  `transfer`, `site_api`.
- **[факт V2] Распределение** — `CallbackDistributor` принимает только заявки канала «Обратный звонок»
  (`ContactChannel::CALLBACK`), заявки без `distribution_state = pending` не трогает.
- **[факт V2] Аудит** — `AuditLogger::asSystem($basis, …)` пишет системное действие с основанием; ключи секретов
  вырезаются. История заявки — аудит + комментарии (`OrderController::history`), доступ — `OrderPolicy::viewHistory`
  (`orders.history` + видимость заявки по области салонов).
- **[факт V2] Шаблон надёжного приёма** (API сайта, этап 8): входящая запись сохраняется до ответа, задание очереди
  несёт только id и ставится после фиксации (`afterCommit`), очередь `site-requests` на драйвере `database`, до
  5 попыток с задержками, состояние «Ошибка», ручной повтор с аудитом, команды восстановления
  `site-requests:process` и `site-requests:retry-failed` (`SiteRequestProcessor`).

### 2.2. События

**`POST /events/call` — уведомление о вызове (3.1.2, с. 16–22).**
- `entry_id` — идентификатор **группы вызовов**, не меняется при переадресации и переводе.
- `call_id` — идентификатор **плеча**.
- `timestamp` — «время события, UTC+3».
- `seq` — счётчик последовательности уведомлений по вызову.
- `call_state`: `Appeared`, `Connected`, `OnHold`, `Disconnected`.
- `location`: `ivr`, `queue`, `abonent`.
- `from` и `to`:
  - `extension` — внутренний номер сотрудника, «не передаётся», если сотрудника определить не удалось;
  - `number` — номер или SIP;
  - в `from` — `taken_from_call_id`; в `to` — `line_number` (входящая линия ВАТС) и `acd_group`;
  - флаги `was_transferred` и `hold_initiator`.
- `disconnect_reason`, `transfer` (`consultative` | `blind` | `return_blind`), `sip_call_id`, `command_id`,
  `task_id`, `callback_initiator`.
- Документировано:
  - уведомления могут прийти не в том порядке, в каком произошли, потому что отправляются параллельно;
    нужно упорядочивать по `seq` или игнорировать событие с меньшим `seq`;
  - начальное состояние может быть любым, конечное — `Disconnected`;
  - если вызов пришёл в нерабочее время абонента, `/events/call` **не отправляется**.
- По примерам (с. 337–349) `seq` начинается с 1 у каждого нового `call_id` внутри одного `entry_id`, то есть
  счётчик относится к плечу. Явной формулировки «по плечу» в таблице нет.

**`POST /events/summary` — завершение вызова (3.1.6, с. 27–31).** Финализирующее событие: после него вызов
можно считать завершённым. Поля:
- `entry_id`;
- `call_direction`: 0 — внутренний, 1 — входящий, 2 — исходящий;
- `from.extension` и `from.number` — при входящем звонке номер звонящего, **не передаётся**, если АОН не
  определён;
- `to.extension` и `to.number`:
  - успешный звонок — тот, кто ответил;
  - пропущенный — первое звено цепочки;
  - номер устройства не передаётся при дозвоне на несколько устройств;
- `line_number` — линия входящего или исходящего;
- `create_time`, `forward_time`, `talk_time` (0, если разговора не было), `end_time` — UTC+3;
- `entry_result`: 1 — разговор состоялся, 0 — пропущен;
- `disconnect_reason`, `sip_call_id`.

**Нет:** `call_id`, `seq`, списка плеч.

**`POST /events/recording` — процесс записи (3.1.4, с. 22–26).**
- `recording_id`, `recording_state`: `Started` → `Continued` (запись перешла в другой `call_id`) → `Completed`.
- `seq` по записи, `entry_id`, `call_id`, `extension`, `timestamp`.
- `completion_code`: 1000 — успешно, 4002 — запись короче минимальной и не сохраняется.
- `recipient`: `Cloud`, `Mail`, `CloudAndMail`.
- `command_id`.

**`POST /events/record/added` — запись помещена в облачное хранилище и готова к скачиванию (3.1.8, с. 32).**
- Поля: `entry_id`, `product_id`, `user_id`, `timestamp`, `recording_id`.
- `user_id` — **id сотрудника в ВАТС, а не внутренний номер**; `-1`, если связать не удалось.
- Примечание Mango: при нагрузке запись «иногда не сразу доступна по API».

Также есть `/events/sms`, `/events/dtmf`, `/events/record/tagged` (3.1.3, 3.1.5, 3.1.7) — для этапа не нужны.

### 2.3. Идентификаторы

- **`entry_id`** — звонок как целое (группа вызовов). Ключ звонка в V2.
- **`call_id`** — плечо: перевод, переадресация и замещение абонента создают новые `call_id` с тем же
  `entry_id`, связь — через `from.taken_from_call_id` (примеры переводов, с. 343–349).
- **`recording_id`** — запись; одна запись может продолжаться через несколько `call_id` (`Continued`).
- Уникальность: в описаниях `entry_id`, `call_id` и `recording_id` сказано, что уникальность гарантируется ВАТС
  «на протяжении всего периода оказания услуг по данному API», а формат может меняться (3.1.2 и 3.1.4; таблица
  извлечена с искажениями). Глобальна ли уникальность между разными ВАТС — **[не документировано]**. Поэтому в
  V2 все ключи берутся вместе с подключением.
- **Отдельного UUID у webhook нет.** Повтор события распознаётся только по содержимому: `entry_id` + `call_id` +
  `seq` для `/events/call` и `entry_id` для `/events/summary`.

### 2.4. Номера, линии, SIP, внутренние номера

- Внутренний номер — «идентификатор сотрудника ВАТС», задаётся в Личном кабинете (определения, с. 7). Приходит
  в `from.extension` / `to.extension` (3.1.2) и `from.extension` / `to.extension` в summary (3.1.6). Список
  сотрудников с внутренними номерами можно получить через `POST /vpbx/config/users/request` (3.7.1, с. 109).
- Линия: `to.line_number` в `/events/call` (3.1.2), `line_number` в summary (3.1.6). По примерам приходит и
  телефон (`7800123456789`, 13 цифр), и SIP (`sip:line00000@tech.mangosip.ru`).
- Номер клиента — `from.number` (входящий) или `to.number` (исходящий). Может быть SIP (`sip:user@…mangosip.ru`)
  или отсутствовать (АОН не определён).

### 2.5. Направления

Направление явно передаётся только в summary (`call_direction`, 3.1.6). В `/events/call` его нет — его можно
только вывести из полей: внешний `from.number` и `to.line_number` — входящий; `from.extension` — исходящий или
внутренний; `command_id`, `callback_initiator`, `task_id` — звонок, начатый командой или обратным звонком Mango
(3.1.2, 3.2). Правило вывода — **[не документировано]**: его нужно проверить на реальных событиях.

### 2.6. Записи разговоров

- После окончания разговора сохранение записи занимает время; Mango рекомендует повторять запрос, например раз
  в минуту. Записи хранятся в облачном хранилище ЛК; удалённую в ЛК запись по API получить нельзя (3.5, с. 88).
- `POST /vpbx/queries/recording/post` (`recording_id`, `action` = `download` | `play`) возвращает `302` на
  временную ссылку. Ссылка одноразовая, её **нельзя сохранять**. Это «наиболее защищённый способ» (3.5.1, с. 88).
  Пример: `POST https://app.mango-office.ru/vpbx/queries/recording/post` с полями `vpbx_api_key`, `sign`, `json`
  → `302 Found`, `Location: https://files.mango-office.ru/…`; сервис файлов отвечает `200`, `Content-Type:
  audio/mpeg` (3.5.1–3.5.2, с. 88–90). Базовый адрес API — `https://app.mango-office.ru/vpbx/` (2.1.1, с. 11),
  подпись исходящего запроса — `sha256(vpbx_api_key + json + vpbx_api_salt)` (2.4.3, с. 14).
- Ошибки API: HTTP-код и JSON с кодом результата (2.1.1, с. 12); коды — «Список кодов результатов» (с. 332–334):
  `3320` «Запись разговора не найдена», `31xx` неверные параметры/ключ, `21xx`/`22xx` счёт и услуги,
  `5001–5011` перегрузка и технические проблемы. Сразу после разговора запись может быть ещё не сохранена (3.5) —
  `3320` поэтому показывается как «Запись пока недоступна».
- `recording_id` — строка до 128 байт, уникальна в пределах ВАТС; внутренний формат не использовать (3.1.4, с. 23).
  Одинаковое поле есть в `/events/recording` и `/events/record/added`; то, что значения в двух событиях совпадают
  для одной записи, примерами не показано **[проверить на реальной АТС]**. Поля длительности записи в событиях
  нет — длительность не хранится.
- GET-ссылка без авторизации (3.5.2, с. 89; сверено с официальной страницей k.mango-office.ru 30.10.2026):
  `GET /vpbx/queries/recording/link/{recording_id}/{action}/{vpbx_api_key}/{timestamp}/{sign}`, `action` —
  `download` | `play`, `timestamp` — время, до которого действует ссылка (в описании: «Часовой пояс UTC+3»),
  `sign = sha256(vpbx_api_key + timestamp + recording_id + vpbx_api_salt)` — это не подпись JSON-запросов.
  Ответ — `302 Found`, `Location: https://files.mango-office.ru/…`; сервис файлов отвечает `200`, `Content-Type:
  audio/mpeg`, `Content-Length`. Ссылки из перенаправления временные, после первого доступа недействительны,
  сохранять их нельзя. Возможность **по умолчанию выключена и включается в личном кабинете Mango**. Поддержка
  `Range`, `HEAD` и ответа `206` в документации **не описана**.
- Нужна ли для API записей услуга «Речевая аналитика» — неоднозначно: раздел 3.5 говорит о ней перед описанием
  методов. **[не документировано]**, проверить на аккаунте.

### 2.7. Время

Все поля времени описаны как «UTC+3» (3.1.2, 3.1.6). Что именно приходит — обычный Unix timestamp или значение,
сдвинутое на 3 часа, — **[не документировано]**. До проверки на реальном событии время приёма CRM остаётся
опорным, а время Mango хранится отдельно как есть.

### 3.1. Как устроено

- **Маршруты.** `POST /mango/{id}/events/call | summary | record/added`, где `{id}` — номер аккаунта из конфигурации
  `mango.api_key_{id}` / `api_salt_{id}` (`routes/web.php:37–39`). Подключение определяется **по URL**, а не по
  телу запроса.
- **Подпись (пакет, `Base/MangoOffice::getMethodData`, `checkSalt`, `getSign`).** Пакет:
  - сверяет `vpbx_api_key` из тела с ключом аккаунта;
  - считает `sha256(key . json . salt)` по сырой строке `json` и сравнивает нестрогим `==` (не `hash_equals`);
  - при несовпадении отвечает HTTP 420 с кодом 3105 или 3102 через `MangoResponse::send`.
- **Ответ.** Успех — `200 {"status":"ok"}`. Ошибка обработки — `500`: обработка синхронная, до ответа
  (`MangoWebhookController::process`, L40–75). Полный payload пишется в лог-канал `mango` / `records`.
- **Realtime (`handleRealtime`, L38–109).**
  1. Cache-lock `mango:call:{account}:{sha1(entry)}`, 10 с.
  2. `MangoCall::firstOrCreate(account, entry_id)`.
  3. `seq` хранится в JSON `call_sequences` по `call_id`; событие с `seq` не больше сохранённого
     игнорируется (L58–63).
  4. Направление вычисляет `MangoCallData`, исходящее не перекрашивается во входящее (L66–79).
  5. На входящем `Appeared` в `ivr` / `queue` / `abonent` ищется заявка, при отсутствии создаётся. Popup
     отправляется один раз.
  6. На `Connected` в `abonent` по внутреннему номеру назначается ответивший (L327–410).
  7. Общей DB-транзакции нет.
- **Summary (`handleSummary`, L111–277).**
  1. **Другой** cache-lock `mango:summary:…`, 15 с, плюс транзакция и `lockForUpdate` по `MangoCall`.
  2. Флаг `summary_processed` защищает от повторной обработки.
  3. При необходимости создаётся входящая заявка; разговор или пропуск определяется по `talk_time`.
  4. Пишется история `ActivityLog` (типы `'5'`, `'6'`, `'7'`), `MissedCall`, задание `ProcessCall` после фиксации.
- **Запись (`handleRecording`, L279–325; `ProcessRecord`).**
  1. `MangoCallRecording::firstOrCreate(['recording_id'])`.
  2. Задание через минуту, до 10 попыток раз в 60 с: ждёт запись истории `ActivityLog` с этим `entry_id` и
     прикрепляет к ней `recording_id`.
- **Прослушивание (`RecordController`).** Ссылка 3.5.2 со сроком сутки; `getAudio` проксирует поток,
  `getAudio2` перенаправляет, `getAudio3` скачивает. Маршруты `record2` / `record3` объявлены вне группы
  авторизации (`routes/api.php:191–192`).
- **Линия → сайт (`MangoSiteResolver`).** Совпадение по `phone`, `second_phone`, `sip` с вариантами `+7`, `8`,
  `sip:` и `LIKE`, затем `latest('updated_at')->first()`.
- **Поиск заявки (`findOrder`, L451–467).** Салон + четыре телефонных поля в вариантах `7` / `+7` / `8`, порядок
  `updated_at desc, id desc`.

### 3.2. Сохранить (как идею, не код)

- Звонок как одна запись на «аккаунт + `entry_id`» с уникальным индексом.
- Отбрасывание устаревших событий по `seq` **в пределах `call_id`**.
- Однократная обработка итога (флаг завершения).
- Ответивший определяется по `Connected` плеча с `to.extension`. Summary не перезаписывает уже зафиксированного
  ответившего: по комментарию в коде, в summary иногда «первый добавочный из очереди».
- Классификатор звонков (`MangoCallData`):
  - номер с `sip:`, `@` или `mangosip.ru` не считается телефоном клиента;
  - `command_id` без `taken_from_call_id`, а также `callback_initiator` и `task_id` — технический или исходящий
    звонок, а не входящее обращение;
  - исходящий `entry_id` не становится входящим.
- Поиск заявки салона «последняя изменённая, затем id» — совпадает с решением V2.
- Побочные эффекты после фиксации транзакции (`afterCommit`).
- Пауза и повторы при прикреплении записи — с учётом документированной задержки Mango.

### 3.3. Не переносить

- **Разные блокировки realtime и summary**, realtime без транзакции. Realtime создаёт заявку на `Appeared`, а
  summary под своей блокировкой может не увидеть её и создать вторую. Поздний realtime после summary
  перезаписывает `status`. Это риск по коду, не воспроизведённая гонка.
- **Числовые исключения:**
  - аккаунт Mango равен id салона (`resolveShowroomId` возвращает `$accountId`);
  - ACD-группы `300`, `400`, `776` переводят звонок в «парный салон» (L586–593);
  - `operator_id = 1000` с 8:00 до 20:00 по времени сервера;
  - `source_id = 20` / `25`, `status_id = 1`;
  - имена «Новый клиент» и «Пропущенный звонок» как признак состояния;
  - типы истории `'5'`, `'6'`, `'7'`.
- **Идентификаторы без аккаунта:** `mango_call_recordings.recording_id` уникален глобально; поиск истории
  (`upsertHistory`, `ProcessRecord`) идёт по `entry_id` без аккаунта.
- **Поиск линии «первый попавшийся»** через `LIKE` и `latest('updated_at')->first()`.
- **Оператор по внутреннему номеру** — через поле `work_place` с фильтром «работает сегодня» по календарному дню
  сервера; при нескольких совпадениях берётся последний изменённый.
- **Нестрогое сравнение подписи; полный payload с номерами клиентов в логах.**
- **Публичный канал** с данными клиента (`MangoIncome`; аудит, раздел 13) и **неавторизованные маршруты записей**.
- **Синхронная обработка до ответа и `500` при ошибке.** Как Mango реагирует на `500`, не документировано;
  если Mango не повторяет запрос, событие теряется.

## 4. Согласованное поведение V2 (вход для проектирования)

Решения пользователя (PROJECT_SPEC.md, разделы 6 и 8; задание 29.10.2026):
- основной номер заявки — `orders.phone`, дополнительные — `order_phones`;
- поиск только по полному нормализованному номеру, в пределах определённого салона;
- если подходящих заявок несколько — последняя изменённая, при равенстве стабильный порядок;
- если подходящей нет — новая заявка;
- новый звонок не сбрасывает статус, результат и расчётную дату заявки;
- события и плечи одного звонка — один звонок, а не несколько заявок; повтор события не создаёт дублей;
- ответивший определяется по внутреннему номеру;
- каждый звонок хранится отдельно;
- история и записи — по правам и области видимости заявки;
- прямые звонки не распределяются;
- софтфон, click-to-call, Calltracking и Calltouch в этап не входят.

## 6. Минимальная схема хранения [предложение]

Имена условные. Одна телефония, без общей платформы всех провайдеров.

1. **`integration_connections.webhook_key`** — случайный ключ адреса, уникальный, по одному на подключение.
   Базовый адрес для ЛК Mango — `https://<crm>/api/mango/{webhook_key}/`, Mango сам добавляет
   `events/call` и т. д. (2.2). Ключ адреса не секрет подписи: подлинность даёт только `sign`. Причина: ключ
   VPBX хранится зашифрованным и искать по нему нельзя. Замена ключа адреса — действие полного администратора с
   аудитом.
2. **`mango_events`** — журнал принятых событий (аналог `site_callback_requests`):
   - поля: `id`, `integration_connection_id`, `kind` (`call` | `summary` | `recording` | `record_added`),
     `entry_id`, `call_id`, `seq`, `recording_id`, `payload_hash` (sha256 сырой строки `json`), `payload`
     (сырой `json`);
   - время: `received_at`, `processed_at`;
   - обработка: `state` (`accepted` | `processed` | `failed` | `ignored`), `attempts`, `error_code`;
   - уникальность `(integration_connection_id, kind, payload_hash)` — побайтовый повтор не сохраняется дважды;
   - индекс `(integration_connection_id, entry_id)`.
3. **`calls`** — звонок, один на «подключение + `entry_id`», уникальный индекс:
   - связи: `showroom_id`, `source_id`, `integration_line_id`, `order_id` (все nullable);
   - направление и номера: `direction`, `line_number` (сырой), `client_phone` (нормализованный или NULL),
     `client_number_raw` (для разбора);
   - ответивший: `answered_by_id` (сотрудник или NULL), `answered_extension`;
   - результат: `status` (`in_progress` | `finished`), `result` (`answered` | `missed` | NULL),
     `resolution` (`linked` | `unknown_line` | `no_client_phone` | `source_unavailable` | `ignored`);
   - время: `started_at`, `answered_at`, `ended_at`, `talk_seconds`, `disconnect_reason`,
     `summary_received_at`, `created_order` (bool).
4. **`call_legs`** — плечо `(call_id, mango_call_id)` уникально: `last_seq`, `state`, `from_extension`,
   `from_number`, `to_extension`, `to_number`, `taken_from_call_id`, `transfer`, `connected_at`, `ended_at`,
   `disconnect_reason`.
5. **`call_recordings`** — `(integration_connection_id, recording_id)` уникально: `call_id`, `entry_id`,
   `mango_user_id`, `state`, `completion_code`, `recorded_at`.
6. **`telephony_extensions`** — внутренний номер `(integration_connection_id, extension)` уникально → `user_id`.
   У сотрудника может быть по номеру в нескольких аккаунтах. Пользователь — только активный и с доступом к салону
   звонка, иначе «не сопоставлен».
7. **Заявка:**
   - новое происхождение `OrderOrigin::Phone` («Звонок»);
   - канал `direct-call`;
   - `distribution_state = NULL` — не распределяется;
   - время и расчётная дата — по `BusinessDayCalculator` салона от времени приёма первого события;
   - связь звонка с заявкой — `calls.order_id`, обратной ссылки в `orders` нет.

Записи аудита: создание заявки звонком — `order.created` с основанием `asSystem('mango')`. Сам звонок — запись
`calls`, а не текст аудита. В ленту карточки звонки добавляются чтением `calls` (раздел 6 PROJECT_SPEC).

## 7. Подпись, дедупликация, блокировки, порядок [предложение]

- **Приём.** Контроллер в `routes/api.php` (без CSRF и сессии):
  1. найти подключение по `webhook_key`; нет такого — `404`;
  2. сверить `vpbx_api_key` и `sign` через `hash_equals`, по сырому `json` из тела формы; ошибка — `403` без
     подробностей, без сохранения и без payload в логе;
  3. сохранить событие в `mango_events`; повтор по уникальному индексу — тихий успех;
  4. поставить задание `afterCommit` и ответить `200`.

  Неактивное подключение: событие сохраняется со статусом `ignored` и отвечается `200`, чтобы его можно было
  разобрать вручную. Лимит запросов — как у API сайта. IP-список Mango — дополнительно, если CRM видит
  настоящий IP (доверенные прокси).
- **Дедупликация в три уровня:**
  1. побайтовый повтор — уникальный `payload_hash`;
  2. повтор с другим порядком полей — `seq` плеча не больше `last_seq`, событие отбрасывается;
  3. повтор summary — `summary_received_at` уже задан.

  Заявка: создаётся только если `calls.order_id` пуст, под блокировкой строки звонка; запись связи — в той же
  транзакции.
- **Одна блокировка для всех событий звонка.** Строка `calls` создаётся `INSERT … ON DUPLICATE` (или
  `firstOrCreate` с повтором при нарушении уникальности), затем `SELECT … FOR UPDATE`. Realtime, summary и
  записи обрабатываются под этой одной блокировкой в одной транзакции. Cache-lock не используется.
- **Параллельные звонки одного клиента** (разные `entry_id`):
  - поиск и создание заявки идут после `resolveClient` (блокировка `client_phones`, затем клиента) — как в
    `createFromSiteRequest`;
  - вторую заявку на того же клиента и салон отсекает существующий уникальный индекс
    `orders_client_showroom_repeat_unique` с повтором транзакции (`OrderManager::retrying`): повтор находит уже
    созданную заявку.
- **Порядок не предполагается:**
  - события плеча сравниваются по `seq` (3.1.2);
  - summary может прийти раньше realtime — тогда он создаёт звонок и, при необходимости, заявку, а поздний
    realtime дописывает только плечи и не меняет `result`, `ended_at`, ответившего;
  - запись может прийти раньше звонка — создаётся заготовка звонка.
- **Поиск заявки.** Салон звонка; `orders.phone = :phone OR EXISTS(order_phones.phone = :phone)`;
  `ORDER BY updated_at DESC, id DESC LIMIT 1`. Связь звонка с заявкой **не меняет** строку `orders` (и
  `updated_at`), чтобы не сбрасывать статус, результат, расчётную дату и правило «последняя изменённая».
- **Эффекты после фиксации:** уведомления и, позже, запросы записей — только `afterCommit`; их сбой не отменяет
  приём.

## 8. Особые случаи [предложение]

| Случай | Обработка |
| --- | --- |
| Неизвестная линия (нет в `integration_lines` подключения) | Звонок сохраняется (`resolution = unknown_line`), заявка не создаётся, источник и салон не угадываются. Виден полному администратору в списке «Неразобранные звонки»; после привязки линии — ручной повтор обработки с аудитом |
| Источник линии отключён, у источника нет канала «Прямой звонок» или салон не разрешён подключению | `resolution = source_unavailable`, без заявки, тот же разбор |
| Неизвестный внутренний номер | Звонок связывается с заявкой как обычно; `answered_extension` сохраняется, `answered_by_id = NULL`; в карточке «внутр. 123 — не сопоставлен». Сотрудник не создаётся, первый найденный пользователь не подставляется |
| Скрытый или некорректный номер (нет `from.number`, SIP, не российский 11-значный) | `client_phone = NULL`, `resolution = no_client_phone`; заявка не создаётся (основной номер обязателен), фиктивный клиент не заводится; звонок виден в разборе с салоном по линии |
| Пропущенный (`entry_result = 0`, `talk_time = 0`) | Тот же шаг «найти или создать» — правило не зависит от ответа; `result = missed`; статус и ответственный заявки не меняются; распределения нет |
| Перевод между сотрудниками | Плечи одного звонка; ответивший — первый `Connected` с `to.extension`, остальные участники видны по плечам. Кого считать ответившим при переводе, из summary не определяется: при нескольких ответивших смысл `to` **[не документирован]** |
| Нет или задержан summary | Заявка уже создана или связана по realtime. Команда проверки (раз в N минут) отмечает звонки без итога старше порога: если все плечи `Disconnected` — `finished` с результатом по плечам (был `Connected` — разговор), иначе «итог не получен». Поздний summary всё равно применяется. Сверка через API статистики (3.4, с. 66–88) — отдельной задачей |
| Нет realtime (нерабочее время абонента, 3.1.2) | Всё делается по summary |
| Звонок, начатый командой или обратным звонком Mango (`command_id` без `taken_from_call_id`, `callback_initiator`, `task_id`) | Не новое входящее обращение; заявку не создавать |

## 9. Ошибки и восстановление очереди [предложение]

Шаблон `SiteRequestProcessor`:
- очередь `mango-events` (драйвер `database`), задание несёт id события, `afterCommit`;
- до 5 попыток с задержками, затем `failed` с безопасным кодом ошибки — без номеров и payload в логах;
- сбой постановки в очередь не теряет событие;
- команды `mango-events:process` (принятые события старше N секунд, по возрастанию id) и
  `mango-events:retry-failed`;
- ручной повтор с аудитом;
- события одного звонка безопасно обрабатывать в любом порядке и повторно (раздел 7).

Для эксплуатации нужен постоянный обработчик очереди и планировщик — сейчас они не настроены (раздел 1.2).

## 10. Открытые вопросы, блокирующие работу

1. **Ответственный по звонку.** Предложение по умолчанию:
   - новая заявка, созданная звонком с известным ответившим, получает его ответственным;
   - у существующей заявки ответственный не меняется;
   - пропущенный звонок — без ответственного.

   Нужно подтверждение: это изменение бизнес-поведения.
2. **Права на звонки и записи.** Предложение:
   - звонки в ленте карточки — по `orders.history`;
   - прослушивание записей — новое право `orders.recordings` вместе с видимостью заявки.
3. **Публичный HTTPS-адрес CRM для Mango** (TLS 1.2, доступ с IP Mango). Без него невозможна ручная приёмка с
   реальной АТС, но реализация и тесты возможны.

Не блокируют, проверяются на первом реальном событии тестовой АТС:
- смысл «UTC+3» во времени;
- Content-Type;
- повторы Mango при не-2xx;

## 12. Реализовано в подэтапе 9а (READY_FOR_REVIEW, 29.10.2026)

Подэтап «Mango VPBX: приём событий звонков и связь с заявками». С реальной АТС не проверялся: всё ниже
подтверждено только тестами на `mangov2_test` с данными по примерам документации.

### 12.1. Приём

- Адрес для ЛК Mango: `https://<crm>/api/mango/{webhook_key}/`; Mango добавляет `events/call` и т. д.
  `integration_connections.webhook_key` — 40 случайных символов, выдаётся каждому подключению (существующим —
  миграцией). Ключ адреса не заменяет подпись. Замена ключа адреса в этом подэтапе не сделана.
- Параметры `vpbx_api_key`, `sign`, `json` читаются как поля формы (`application/x-www-form-urlencoded`);
  JSON-тело с теми же полями тоже принимается.
- Подпись: `hash_equals` для `vpbx_api_key` и для `sha256(vpbx_api_key + json + vpbx_api_salt)` по строке
  `json` в том виде, в каком она пришла. JSON разбирается только после проверки подписи.
- Ответы — без тела:

| Код | Когда |
| --- | --- |
| 404 | Путь не из документации или неизвестный ключ адреса |
| 403 | Подключение отключено; неверный `vpbx_api_key` или `sign` |
| 400 | Нет поля, `json` больше 64 КБ; после верной подписи — структура не по контракту (событие не сохраняется) |
| 503 | Событие не удалось сохранить в БД |
| 200 | Событие сохранено (или это повтор уже сохранённого); `record/tagged`, `sms`, `dtmf` — подпись проверена, событие не сохраняется. С подэтапа 9б `recording` и `record/added` сохраняются (раздел 13) |

- 200 отдаётся только после фиксации записи `mango_events`. Подпись и ключи не хранятся. Сырой `json` хранится
  один раз — в `mango_events.payload` (скрыт из сериализации). В журнал пишутся только id подключения и путь
  события, без ключа, подписи и payload.
- Повтор события: уникальный `(integration_connection_id, dedup_key)`, где ключ — sha256 от
  `call|entry_id|call_id|seq` или `summary|entry_id`. Повтор с другим порядком полей тоже распознаётся;
  повторный summary с другим содержимым игнорируется (применяется первый).

### 12.2. Очередь и восстановление

- Задание `ProcessMangoEvent` (очередь `mango-events`, `afterCommit`, 5 попыток, задержки 10 с, 1 мин, 5 мин,
  30 мин). После последней попытки или неповторяемой ошибки (`invalid_payload`) — состояние «Ошибка» с кодом
  (подробности ошибки — только безопасные, см. 12.9).
  Сбой постановки в очередь не теряет событие: оно остаётся «Принято» с кодом `not_queued`.
- Команды:
  - `php artisan mango-events:process --limit= --older-than=` — принятые, но не обработанные события;
  - `php artisan mango-events:retry-failed --limit= --event=` — повтор ошибочных (аудит `mango_event.retried`);
  - `php artisan mango-calls:rematch --connection= --call= --limit=` — повтор сопоставления звонков на разборе
    после исправления линий и внутренних номеров (аудит `mango_call.rematched`).
- Планировщик и постоянный обработчик очереди в эксплуатации по-прежнему не настроены — как и для API сайта.
  Обработчик: `php artisan queue:work --queue=mango-events`.

### 12.3. Звонок, плечи, порядок, блокировки

- Звонок — `calls` с уникальным `(integration_connection_id, entry_id)`; плечо — `call_legs` с уникальным
  `(call_id, mango_call_id)` и `taken_from_call_id`. Одинаковый `entry_id` в разных подключениях — разные звонки.
- Все события звонка обрабатываются в одной транзакции под блокировкой строки `calls`
  (`INSERT IGNORE`, затем `SELECT … FOR UPDATE`); данные плеч читаются блокирующим чтением. Порядок блокировок:
  событие → звонок → `client_phones` → клиент → заявка. Внешних HTTP-запросов внутри транзакции нет. Гонку двух
  звонков одного нового клиента решают уникальные индексы `client_phones_phone_unique` и
  `orders_client_showroom_repeat_unique` с повтором всей транзакции.
- `seq` сравнивается только внутри плеча: состояние плеча меняет событие с большим `seq`, а факты (момент
  появления, соединения, завершения) берутся из любого события, поэтому позднее старое событие ничего не
  откатывает.
- Summary может прийти раньше realtime: он задаёт итог, поздний realtime только дописывает плечи и ответивших.

### 12.4. Время

Поля времени Mango (`timestamp`, `create_time`, `talk_time`, `end_time`) читаются как обычный Unix timestamp
(абсолютный момент), без добавления 3 часов. Основание: документация называет их «unix время» (3.4) и пишет
«UTC+3» как зону показа; Unix timestamp от зоны не зависит. Если реальная АТС пришлёт сдвинутые значения, это
будет видно сразу (время звонков на 3 часа позже) — проверить на первом событии.

`event_at` новой заявки — начало звонка по Mango, расчётная дата — по правилу салона от этого момента, а не от
времени обработки задания. `received_at` — время приёма первого события звонка CRM.

### 12.5. Направление, итог, длительность

- Направление: из summary (`call_direction`), до него — по корневым плечам: внешний `from.number` + линия без
  `from.extension` → входящий; только `from.extension` → исходящий; внутренние номера с обеих сторон →
  внутренний.
- Технический звонок (не создаёт заявку): `command_id` без `taken_from_call_id`, `callback_initiator` или
  `task_id` у корневого плеча. `command_id` вместе с `taken_from_call_id` — маршрутизация входящего, не
  технический.
- `talk_time` summary — момент ответа (0, если разговора не было). Длительность = `end_time − talk_time`;
  отвечен = `entry_result = 1` и `talk_time > 0` (в примере 2 раздела 3.1.6 `entry_result = 1` при
  `talk_time = 0`). Без summary длительность не показывается.

### 12.6. Источник, салон, заявка

- Линия → источник → салон только через `integration_lines` подключения: телефон по `match_key`, SIP — с
  префиксом `sip:` и без него. Нет линии — «Неизвестная линия», несколько — «Неоднозначная линия»; источник
  отключён, перенесён, салон не активен или не разрешён подключению, нет активного канала «Прямой звонок» —
  «Источник недоступен». Звонок сохраняется без заявки, виден на разборе, сопоставление можно повторить.
- Номер клиента: скрытый, SIP или не российский 11-значный — «Нет номера клиента», без заявки и без клиента.
- Поиск заявки — в салоне линии по `orders.phone`, `order_phones` и номерам клиента; при нескольких —
  последняя изменённая, затем больший id.
- Новую заявку создаёт только прямой входящий звонок: канал «Прямой звонок», происхождение `mango_vpbx`
  («Mango VPBX»), начальный статус, без распределения, аудит `order.created` с основанием `mango_vpbx`.
  Исходящий звонок только присоединяется к существующей заявке, внутренний и технический — не привязываются.
- Существующая заявка: статус, причины, даты, источник, счётчик повторов и `updated_at` не меняются (звонок
  ссылается на заявку через `calls.order_id`).

### 12.7. Внутренние номера и ответственный

- `telephony_extensions`: строка до 32 символов, уникальна внутри подключения; тот же номер в другом подключении
  допустим. Управляет полный администратор с `connections.manage` (аудит добавления и удаления).
- Допустимый сотрудник: активен, есть `orders.view`, есть доступ к салону звонка (глобальный или по салонам).
  График не учитывается.
- Ответивший — по плечам: соединение клиента с внутренним номером (`Connected`, где внутренний номер есть ровно
  у одной стороны). Консультация (`Connected` между двумя внутренними номерами) ответом не считается. Если плеч
  нет — `to.extension` summary и `talk_time`.
- **Окончательное правило ответственного (решение пользователя 29.10.2026). Прежнее автоматическое
  переназначение на последнего ответившего отменено**, как и механизм «более новое соединение переназначает
  заявку» (`orders.call_assigned_at` удалено миграцией `2026_10_29_210000_revise_mango_call_assignment`).
  Mango только заполняет пустой `responsible_id` и никогда его не меняет:
  - новая заявка — ответственный фактически ответивший сопоставленный допустимый сотрудник; без такого — без
    ответственного;
  - существующая заявка без ответственного — получает фактически ответившего допустимого сотрудника (версия
    заявки увеличивается, аудит `order.responsible_changed` с основанием `mango_vpbx`);
  - заполненный ответственный не меняется, даже если ответил другой сотрудник; перевод, пропущенный звонок и
    неизвестный внутренний номер назначение не меняют и не снимают;
  - временный доступ к чужой заявке не выдаётся.
- Ответившие и переводы сохраняются независимо от ответственного: `call_legs.answered_by_id` у каждого плеча,
  `calls.answered_by_id` — самый ранний соединившийся с клиентом допустимый сотрудник.
- Порядок событий: для ещё неназначенной заявки берётся самое раннее по моменту соединения достоверное
  соединение с допустимым сотрудником из известных к этому моменту фактов звонка. Если в один момент соединились
  разные сотрудники — никто не назначается, звонок на разборе; если ни один ответивший не сопоставлен с
  допустимым сотрудником — тоже на разборе. После назначения запоздалые события его не пересматривают.
- Однократность: звонок предлагает ответившего своей заявке один раз — в первой обработке, где известны и
  заявка, и допустимый ответивший (`calls.assignment_decided_at`; `assigned_user_id` и `assigned_connected_at` —
  кого и по какому соединению звонок действительно назначил). Повтор webhook, задания или rematch и поздние плечи
  уже решившего звонка ничего не назначают и не пишут аудит, поэтому ручное снятие ответственного не отменяется
  старым звонком.
- Атомарность: проверка `responsible_id IS NULL` и назначение — под блокировкой строки заявки
  (`OrderManager::assignFromCall`), которую берут и ручное изменение, «Взять», распределение и передача. Кто
  первым заполнил ответственного (вручную, распределением, другим звонком), тот и остаётся.

### 12.8. Карточка и администрирование

- Блок «Звонки» в карточке заявки — по `orders.history` и доступу к заявке, загружается по запросу: направление,
  начало и конец, состояние, пропущен, длительность (только из summary), ответивший или «внутр. X — сотрудник не
  сопоставлен», источник и линия, плечи при переводе. Кнопок прослушивания нет; `orders.recordings` — следующий
  подэтап.
- «Подключения» → действие «Приём событий» (полный администратор с `connections.manage`): адрес для ЛК Mango,
  последнее событие, счётчики (на разбор, ошибки, в очереди), внутренние номера, звонки на разбор с повтором
  сопоставления, события с ошибками с повтором. Ключ, соль, подпись и payload не показываются. Подключение
  остаётся «Не проверено».

### 12.9. Не сделано и известные ограничения

- Записи разговоров, уведомления, popup, click-to-call, софтфон, Calltracking, Calltouch, импорт истории V1.
- Команда «нет итога» (закрытие звонков без summary) не сделана: карточка показывает «Завершён, итог от Mango
  не получен», если все плечи завершены.
- Замена ключа адреса из интерфейса не сделана.
- Не проверено на реальной АТС: смысл времени, Content-Type, повторы Mango при не-2xx, формат `line_number`,
  поведение `to.extension` в summary при переводе, IP отправителей.
- Безопасные ошибки (29.10.2026): любая ошибка обработки события или повтора сопоставления заменяется
  `MangoEventFailure` без исходного исключения в цепочке. В журнал приложения, вывод обработчика очереди и
  `failed_jobs` попадают только код ошибки, класс исключения, SQLSTATE, id события (звонка) и подключения;
  в `mango_events.error_code` — только код. Значения SQL-параметров, телефоны, исходный JSON и ключи не
  сохраняются. Повторная обработка (`mango-events:retry-failed`, кнопка «Повторить») работает как прежде. На
  29.10.2026 в рабочей базе событий Mango и записей `failed_jobs` нет, в `storage/logs` записей Mango нет.
  Для API сайта (этап 8) эта правка не делалась.
- Ограничения частоты запросов на адресе приёма нет (как и у API сайта).

## 13. Реализовано в подэтапе 9б: записи разговоров (READY_FOR_REVIEW, 30.10.2026, доработка — воспроизведение из Mango)

Контракт подтверждён по MangoOffice_VPBX_API v1.9 и официальной странице 3.5.2 (раздел 2.6 выше: 2.1.1, 3.1.4,
3.1.8, 3.5, 3.5.2, коды результатов). Обмен с реальной АТС **не проверен**.

**Аудио хранится в Mango. CRM хранит только сведения о записи** и воспроизводит её через защищённый поток.
Первая версия 9б (фоновое скачивание в `storage/app/recordings` по 3.5.1) заменена: задание `FetchCallRecording`,
очередь `mango-recordings`, команда `mango-recordings:fetch`, повтор получения в разделе администратора и диск
`recordings` удалены. На 30.10.2026 в рабочей базе записей разговоров и заданий `mango-recordings` не было,
каталога `storage/app/recordings` нет (0 файлов, 0 байт) — удалять нечего.

### 13.1. Приём событий

- `POST /api/mango/{webhook_key}/events/recording` и `/events/record/added` проходят ту же проверку подписи и
  сохраняются в `mango_events` до ответа 200 (виды `recording`, `record_added`). Обязательные поля:
  `recording` — `recording_id`, `recording_state` (Started/Continued/Completed), `seq`, `entry_id`, `call_id`,
  `timestamp`; `record/added` — `recording_id`, `entry_id`, `timestamp`. Иначе — 400, событие не сохраняется.
- Дедупликация: `recording|recording_id|seq` и `record_added|recording_id`. Обработка — та же очередь
  `mango-events`, те же попытки и команды восстановления (`mango-events:process`, `retry-failed`).
- Событие записи не создаёт звонок и заявку и не меняет их. Запись пришла раньше звонка — `call_id` пуст; событие
  звонка с тем же `entry_id` связывает её. Гонку исключает блокировка: событие записи читает строку звонка (или
  промежуток индекса) `FOR UPDATE`.
- Состояния: `Started`/`Continued` — «Запись не завершена»; `Completed` с кодом 1000 в облако или
  `record/added` — «Запись в Mango» (Mango сообщила о записи; это не гарантия, что воспроизведение сейчас
  удастся); `Completed` с другим кодом (например 4002) или `recipient = Mail` — «Не сохранена в Mango»;
  последующий `record/added` возвращает «Запись в Mango». После события запросов к Mango и заданий нет.

### 13.2. Хранение

- Таблица `call_recordings`: подключение, `recording_id`, `entry_id`, `mango_call_id` (плечо из события с
  наибольшим `seq`), внутренний номер, `call_id` (после сопоставления), состояние, код завершения и получатель
  из события, время `record/added`, причина «не сохранена» (`not_saved_by_mango`, `mail_only`). Уникально
  `(integration_connection_id, recording_id)`: одинаковый id в разных подключениях — разные записи; у звонка
  может быть несколько записей.
- Ссылки Mango (подписанные и из перенаправления), ключ, соль и подпись не хранятся ни в БД, ни в кэше.
- Не используются (колонки удалённого скачивания, оставлены без разрушительной миграции): `available_at`,
  `attempts`, `claim_token`, `claimed_at`, `mango_result`, `file_path`, `mime_type`, `size_bytes`, `ready_at`.
  Миграция `2026_10_30_150000` переводит прежние состояния `fetching`/`ready`/`failed` в `recorded`, ничего не
  удаляя.

### 13.3. Воспроизведение из Mango (`MangoRecordingPlayer`, `CallRecordingController::audio`)

Каждый запрос браузера к маршруту CRM повторяет все шаги; одноразовая ссылка повторно не используется.

1. Новая ссылка 3.5.2: `GET {api_url}queries/recording/link/{rawurlencode(recording_id)}/play/{vpbx_api_key}/
   {timestamp}/{sign}`, `timestamp` = текущее Unix-время + `link_ttl` (300 с, `MANGO_RECORDING_LINK_TTL`) без
   ручного сдвига на 3 часа, `sign = sha256(key + timestamp + recording_id + salt)` по исходному `recording_id`.
2. Без следования перенаправлениям. Принимается только `302` на `https://` хост из `file_hosts` (по умолчанию
   `files.mango-office.ru`, `MANGO_RECORDING_FILE_HOSTS`), порт 443, без логина в адресе; иначе ошибка. Ключ и
   подпись уходят только на адрес API. Ответ не `302` — разбирается код результата (до 4 КБ ответа).
3. Одноразовая ссылка запрашивается один раз, с проверенным `Range` браузера (один диапазон `bytes=a-b`, `a-`,
   `-n`; несколько диапазонов или неверный — не передаются, запрашивается файл целиком). Повторное
   перенаправление сервиса файлов не выполняется.
4. Ответ сервиса файлов передаётся браузеру потоком (`StreamedResponse`, куски по 64 КБ, `flush`); при отключении
   клиента (`connection_aborted`) чтение прекращается и upstream-соединение закрывается.
   - `200` — `Content-Type: audio/mpeg`, `Content-Length` (если есть). `Accept-Ranges: bytes` только если его
     прислал Mango, иначе `none`. На запрос с Range ответ `200` остаётся `200`, 206 не подделывается.
   - `206` — передаются `Content-Range` (проверенный формат), `Content-Length`, тип; `Accept-Ranges: bytes`.
   - `416` — передаётся с `Content-Range: bytes */N`, без тела.
   - Тип не `audio/mpeg`/`audio/mp3`, пустое тело или начало HTML/JSON (для ответа с начала файла) — ошибка, а не
     аудио.
- `HEAD` — только шаг 1–2 (получить ссылку), одноразовая ссылка не запрашивается; `200` или ошибка.
- Без хранения: HTTP-клиент работает с `stream => true` — Guzzle отдаёт сетевой поток через StreamHandler
  (`createSink` возвращает сам поток, без `php://temp`, который при > 2 МБ уходит во временный файл). StreamHandler
  требует `allow_url_fopen`; без него воспроизведение не начинается (`stream_unsupported`). `decode_content` выключен,
  `Accept-Encoding: identity`. Ни постоянных, ни временных аудиофайлов, весь файл в память не читается.
- Транзакция БД во время воспроизведения не открыта. Тайм-ауты: соединение 10 с, заголовки и пауза чтения 30 с,
  общий предел потока `stream_seconds` 3600 с (`set_time_limit`).
- Ошибки — короткий текст `text/plain`, `no-store`: `404` «Запись пока недоступна» (3320, сервис файлов 404/410,
  API 404 без кода), `502` «Не удалось воспроизвести» (остальное: 31xx/2xxx/5xxx, 5xx/429, сеть, чужой хост,
  не аудио, подключение выключено или без ключа/соли). Журнал — id записи и подключения, код ошибки, HTTP-статус и
  код результата Mango; без ссылок, ключа, соли, подписи и ответов Mango. Сообщения сетевых исключений (в них
  адрес) отбрасываются.
- Ограничение частоты маршрута — 120 запросов в минуту на пользователя.

### 13.4. Доступ и прослушивание

- Право `orders.recordings` («Прослушивание записей разговоров»), автоматически — только роль администратора.
  Прослушивание = доступ к заявке + `orders.history` + `orders.recordings`, проверка на каждом запросе (GET, HEAD,
  каждый Range). Запись должна быть «Запись в Mango» и принадлежать звонку этой заявки; запись без связанной
  заявки, «не завершена» и «не сохранена» не отдаются. Отказ в доступе до Mango не доходит.
- `GET|HEAD /orders/{order}/recordings/{recording}/audio`: `Cache-Control: no-store, private`, `nosniff`, без
  `Content-Disposition` и `Location`. В браузер не уходят адрес Mango, ключ, подпись, соль и `recording_id`.
- `POST /orders/{order}/recordings/{recording}/play` (`playback` — UUID воспроизведения, ограничение 60/мин) —
  аудит `order.recording_played` в истории заявки. Один раз на воспроизведение: пауза, перемотка, Range, HEAD и
  «Повторить» после ошибки новых записей не дают; новое воспроизведение — после окончания или перезагрузки.
  Аудит фиксирует начало, а не «прослушано полностью».
- Карточка → «Звонки»: с правом — «Запись N» и состояние («Запись в Mango», «Запись не завершена», «Не сохранена
  в Mango»), плеер `<audio controls preload="none">` только для «Запись в Mango». Ошибка воспроизведения —
  один `HEAD` для уточнения и сообщение «Запись пока недоступна» / «Не удалось воспроизвести» с кнопкой
  «Повторить»; автоматических повторов и опроса нет. Нет записей — «Сведений о записи от Mango нет». Без права
  ключа `recordings` в пропсах нет.
- «Подключения» → «Приём событий»: счётчики «Запись в Mango», «Не завершена», «Не сохранено в Mango», список не
  сохранённых (причина, связь со звонком) и напоминание о включении ссылок в ЛК Mango. Прослушивания и повтора
  получения в разделе администратора нет.
- Заявку записи и воспроизведение не меняют: ответственный, статус, источник, бизнес-дата, повтор, `updated_at`,
  `lock_version`.
- Срок доступности определяет Mango (хранение в облаке ЛК; удалённую в ЛК запись получить нельзя, 3.5); CRM
  доступность дольше этого не обещает.

### 13.5. Настройки Mango, очереди и команды

- В личном кабинете Mango нужно **включить выдачу ссылок на записи разговоров по API** (3.5.2: по умолчанию
  выключено). CRM настройки АТС не меняет.
- Очередь только `mango-events`: `php artisan queue:work --queue=mango-events`. Очередь `mango-recordings` и
  команда `mango-recordings:fetch` больше не нужны. Планировщик, Supervisor и Horizon не настроены.
- Воспроизведение идёт в веб-процессе: длинный поток занимает процесс PHP на время прослушивания (для
  `php artisan serve` — единственный процесс).

### 13.6. Проверено и не проверено

- Проверено HTTP fake (тестовая база): подпись, адрес и срок GET-ссылки; разрешённые и запрещённые
  перенаправления; поток `stream => true` без `sink`, чтение кусками ≤ 64 КБ без чтения тела целиком, без файлов в
  `storage/app`; ответы 200, 206, 416 и 200 на запрос с Range; HEAD без запроса одноразовой ссылки; 3320/404 —
  «Запись пока недоступна», прочие ошибки — «Не удалось воспроизвести» без выдачи HTML/JSON за аудио; права и
  чужие записи; отсутствие секретов в журналах, ответах и БД; отсутствие фонового скачивания после событий;
  метаданные, аудит, неизменность заявки.
- На реальной записи не проверено: включение ссылок в ЛК и ответ API, если оно выключено; толкование `timestamp`
  (в описании «UTC+3»; передаётся Unix-время — при иной трактовке ссылка окажется просроченной или более долгой);
  кодирование `recording_id` с `/`, `=`, `+` в пути; фактический хост перенаправления; поддержка `Range`/`206` и
  `Accept-Ranges` сервисом файлов (без неё перемотка возможна только в уже загруженной части); реальный
  `Content-Type`; формат ошибок; задержка сохранения; совпадение `recording_id` в двух событиях; нужна ли
  «Речевая аналитика»; поведение при отключении браузера через реальный веб-сервер.
- Гонка «запись раньше звонка» в двух процессах автоматически не прогонялась.
