### Что реализовано

- **Автосалоны** (`/showrooms`): серверная пагинация, поиск по коду/названию/адресу/телефону, фильтр статуса,
  создание и редактирование в диалоге, деактивация и повторная активация. Физического удаления нет.
  Технический код салона создаётся сервером из названия и не меняется. Создание доступно только при глобальном доступе.
  Часовой пояс выбирается только из 12 российских поясов, подписанных крупными городами (`app/Support/Timezones.php`).
  Сервер принимает только их (`Rule::in`, «Выберите часовой пояс из списка.»). Если салон был сохранён раньше с
  другим поясом, при редактировании этот пояс остаётся допустимым и показывается в списке.
- **Отделы** (`/departments`): то же для отделов, фильтры по салону (включая «Общие»), типу и статусу.
  Общий колл-центр — отдел с `showroom_id = null`. Тип отдела задаёт назначение, название редактируется.
  Технический код отдела создаётся сервером из названия. Салон, тип и код после создания не меняются.
- **Диалоги добавления и изменения салона и отдела** (`components/organization/form-dialog.tsx`, по образцу ReUI
  `c-alert-dialog-6`) при закрытии с несохранёнными изменениями открывают поверх вложенное подтверждение
  «Закрыть без сохранения?» с кнопками «Продолжить» и «Закрыть». Это касается кнопки «Отмена», крестика, Esc и клика
  мимо. Без изменений и после успешного сохранения диалог закрывается сразу; во время запроса закрыть нельзя.
  Вид `components/ui/dialog.tsx` и `alert-dialog.tsx` приведён к стилю превью ReUI (shadcn `radix-nova`):
  затемнение `bg-black/10` с лёгким размытием, `rounded-xl`, отступ `p-4` и футер-полоса
  `border-t bg-muted/50`. Кнопки, поля и остальные компоненты остались в стиле проекта `radix-maia`.
- **Сотрудники** (`/users`): поиск, серверная пагинация, фильтры по статусу, салону и роли; создание и
  редактирование (`/users/create`, `/users/{id}/edit`); назначение ролей, салонов и отделов; отключение
  и включение; отдельное действие «Задать новый пароль»; выдача и отзыв глобального доступа.
  Пароли и хэши в ответы не попадают. Отключённый сотрудник выходит из системы на следующем запросе,
  его сессии в БД удаляются, `remember_token` меняется.
- **Роли и права** (`/roles`): список, создание, изменение названия и прав (сгруппировано по разделам),
  удаление неиспользуемых ролей. Системная роль администратора защищена: всегда содержит все права,
  не удаляется.
- **Аудит** (`/audit`): кто, когда, объект, безопасное описание; поиск и фильтр по типу объекта.
- **Рабочее место** (`/dashboard`): реальные имя, роли, салоны и отделы сотрудника, без выдуманных метрик.
- **Ошибки**: страница 403/404/419 (в production также 500/503) с понятным текстом; для действий без прав —
  сообщение об ошибке без перехода.
- **Таблицы списков** (21.10.2026): все списки построены на `components/registry-table.tsx` (`RegistryTable`) —
  шапка с числом записей и кнопкой добавления, панель фильтров ReUI Filters, таблица, пагинация. Поиск закреплён в
  панели. Условия: для поиска «содержит / не содержит»; для списков «равно / не равно / любое из / ни одно из», для
  необязательных полей ещё «пусто / не пусто» (общие отделы, без классификации, без агентства, без каналов, без
  ролей; у салона сотрудника «пусто» нет из-за глобального доступа). Меню условия: «Дублировать», «Инвертировать»,
  «Удалить»; условия объединяются через «И». Сервер (`App\Support\TableFilters`, `TableFilter`) принимает
  `filter[i][field|operator|values][]`, отбрасывает неизвестные поля, условия и значения вне области доступа;
  старые ссылки вида `?status=active`, `?classification=none` понимаются как «равно» / «пусто».
- Во всех экранах: загрузка (скелетон таблицы), пустое состояние, ошибки по полям, ошибка сохранения,
  состояние «нет доступа», сообщения об успехе (toast), защита от двойной отправки (кнопки блокируются
  на время запроса), обработка одновременного редактирования (`lock_version`), адаптивность для планшета,
  все действия видимы без наведения.

  Применена к рабочей базе `mangov2` без сброса: салон сохранил выбранный ранее пояс и получил включённую границу
  19:00.
- Форма салона: блок «Расчётный день» (пояс, переключатель `Switch`, время через ReUI Time Picker
  `components/reui/time-picker.tsx` по образцу `c-time-picker-9`); в таблице колонка «Расчётный день».
  Выключенная граница сохраняет время, поэтому при повторном включении прежнее время восстанавливается.
- Источник (с 21.10.2026, по окончательному решению): настроек расчётного дня нет в форме, запросах, ответах
  Inertia и расчёте; источник всегда использует правило своего салона. Поля `business_day_*` в запросе источника
  игнорируются. Колонки `sources.business_day_mode`, `sources.business_day_boundary` и CHECK
  `sources_business_day_check` оставлены в БД неиспользуемыми, чтобы не удалять ранее сохранённые значения;
  новой миграции нет.
- Сервис `App\Services\BusinessDayCalculator` (`ruleFor`, `forShowroom`, `forSource`, `resolve`) по моменту
  события и настройкам салона возвращает `BusinessDay`: дату окончания периода, полуоткрытый период и снимок
  `BusinessDayRule` (пояс, действующая граница или `null` для календарных суток). Текущее время в расчёте не
  используется. Сервис пока никем не вызывается: обращений, распределения и отчётов ещё нет, поэтому сохранённые
  настройки не означают работающего распределения.
- Проверка, права и аудит:
    - поля проверяются на сервере; если их нет в запросе, при создании берутся значения по умолчанию, при
      изменении сохраняются текущие;
    - настройки салона меняются только с правом управления салонами в его области доступа, право на источники для
      этого не даёт;
    - изменения пишутся в аудит, конкурентное редактирование обрабатывается через `lock_version`.

  для него каналы; классификации и каналы в форме ограничены правилами вида.
- **Справочники источников** (`/source-references/{kinds|classifications|channels|agencies}`, одна страница с
  вкладками, общий сервис `SourceReferenceManager`, реестр `App\Support\SourceReferenceType`): создание,
  переименование, порядок, отключение и включение; физического удаления нет (маршрута удаления нет, FK `restrict`).
  У видов, классификаций и каналов есть неизменяемый технический код. Показывается число источников, использующих
  значение, — только по доступным салонам.
    - Виды (`source_kinds`): Сайт `site`, Квиз `quiz`, Бот `bot`, Соцсеть `social`, Классифайд `classified`,
      Партнёр `partner`, Ручной ввод `manual`.
    - Классификации (`source_classifications`, бывшая `site_types`): Реклама, SEO, Реклама/SEO, VA; прежнее значение
      «Классифайд» (`classified`) сохранено и отключено.
    - Каналы (`contact_channels`): Обратный звонок `callback-request`, Прямой звонок `direct-call`, Чат `chat`.
      По уточнению пользователя (20.10.2026) отправка формы сайта с номером клиента — это «Обратный звонок».
      Миграция `2026_10_20_100500_merge_form_channel_into_callback` переименовывает канал `callback-request`
      (id и код сохраняются; если имя «Обратный звонок» занято другим каналом, миграция останавливается с
      понятной ошибкой), переносит связи канала `form` в правилах видов и у источников на `callback-request` без
      дублей, повышает `lock_version` затронутых видов и источников и отключает `form` (запись остаётся, «Форма/заявка»
      видна среди отключённых на вкладке «Каналы»). Другие каналы не меняются; откат миграции данные не трогает.
      Сидер создаёт только три канала и не создаёт `form` повторно. Миграция применена к рабочей БД `mangov2`
      20.10.2026 (без сброса): канал id 1 `callback-request` — «Обратный звонок», `form` отключён, связей у него
      нет, у «Квиза» один канал. Проверки на `mangov2_test`: PHPUnit 142/142, Pint, PHPStan, `npm run check`,
      `types:check`, браузерные сценарии 4/4 — PASS; `npm run build` — NOT_RUN (интерфейс не менялся).
    - Агентства (`agencies`, добавлен `sort_order`).
    - Правила вида (`source_kind_classification`, `source_kind_channel`) редактируются в диалоге вида: Сайт — все
      каналы и Реклама, SEO, Реклама/SEO; Квиз — обратный звонок, те же классификации; остальные —
      все каналы, без классификаций. Новое правило может включать только активные значения.
- **Проверки источника на сервере** (`SourceManager`, транзакция, `sharedLock` связанных записей): новый выбор
  салона, вида, классификации, агентства и каналов должен быть активным и разрешённым для вида. Значения, которые у
  источника уже есть при неизменном виде, сохраняются даже после отключения или изменения правил. При смене вида
  проверяется всё заново.
- **Подключения** — только сохранение настроек, внешние системы не вызываются, состояние всегда «Не проверено»:
    - «Приём заявок с сайта» (`source_site_intakes`, одна запись на источник): активность привязки к будущему
      общему API; область — источник и его салон. Адреса приёма и ключей нет — они выдаются на этапе рабочего API.
    - «Mango VPBX» (`/connections`, `integration_connections` с `provider = mango_vpbx`): название (уникально в
      пределах провайдера), разрешённые салоны (`integration_connection_showroom`, хотя бы один), активность,
      `secrets` (API key и API salt, cast `encrypted:array`, скрыты из сериализации).
    - Привязка источника (`integration_connection_sources`, не больше одной на источник и провайдера) и линии
      (`integration_lines`: тип `phone` или `sip`, исходное значение и ключ сопоставления). Уникальность — индекс
      `(integration_connection_id, type, match_key)`: телефон нормализуется до цифр (`8XXXXXXXXXX` и 10 цифр
      приводятся к `7…`), SIP хранится строкой и сравнивается без учёта регистра, в телефон не преобразуется.
      Составной FK гарантирует, что линия принадлежит аккаунту своей привязки. Одинаковый номер в разных аккаунтах
      допустим; дубль в одной форме и гонка двух сохранений дают ошибку у поля.
    - Источник можно привязать только к подключению, разрешённому для его салона; нельзя убрать из подключения
      салон, источник которого к нему привязан, и нельзя перенести привязанный источник в неразрешённый салон.
    - Привязки и линии редактируются в карточке источника и сохраняются вместе с ней (один `lock_version`).
      Сотрудник без управления подключениями видит их сводку только для чтения; запрос с ними от него — 403.
- **Секреты:** зашифрованы в БД; в списки и данные редактирования не попадают — только признак «задан/не задан»;
  пустое поле сохраняет прежнее значение; замена — вводом нового значения, удаление — отдельным флажком; аудит
  пишет только «API key: задан/заменён/удалён»; ключи `api_key`, `api_salt`, `secrets` вырезаются `AuditLogger` и
  не сохраняются в сессию при ошибке валидации (`dontFlash`). Site ID и Token Mango Calltracking не используются;
  настроек Calltracking и Calltouch в V2 не было и не добавлялось.
- **Права:** `sources.view`, `sources.manage`, `source_references.view`, `source_references.manage` (переименованы
  из `sites.*`, `site_references.*` с сохранением выдачи), `connections.manage`, `connections.secrets`.
  Подключения требуют права **и** полного администратора (активен, глобальный доступ, системная роль
  администратора — `AdministratorGuard::isFullAdministrator`); ввод и удаление секретов — дополнительно
  `connections.secrets`. Единая серверная проверка — `IntegrationConnectionPolicy::viewAny`; её используют
  контроллеры и запросы, а результат передаётся в интерфейс общим свойством `auth.abilities.manageConnections`
  (`HandleInertiaRequests`) и `can.manageConnections` на странице источников. По нему показываются пункт меню
  «Подключения» и раздел подключений в карточке источника; названия ролей в React не проверяются.
    - Источники видны только для доступных салонов: область применяется в запросе до поиска, фильтров и пагинации
      (`AccessScope::sources`); чужой id в фильтре игнорируется; списки выбора содержат только доступные салоны.
      Создание, изменение, отключение в чужом салоне и перенос в чужой салон — 403 (`SourcePolicy`).
    - Справочники общие: изменять их можно только с `source_references.manage` **и** глобальным доступом
      (`Gate source-references.manage`).
- **Аудит:** `source.*` (к старому и новому салону; названия салона, вида, классификации, агентства, каналов,
  состояния приёма с сайта, подключения Mango и линий), `source_kind.*`, `source_classification.*`,
  `contact_channel.*`, `agency.*`, `integration_connection.*`. Старые записи `site.*`, `site_type.*` сохранены и

### Модель доступа

- Роль определяет **действия**, принадлежность к салонам и отделам — **данные**. Одного разрешения недостаточно,
  чтобы увидеть чужой салон.
- Глобальный доступ (`has_global_access`) выдаётся только явно: администратором с правом `access.grant_global`
  и глобальным доступом, не самому себе.
- Сотрудник без глобального доступа видит: свои салоны; отделы этих салонов и общие отделы; сотрудников,
  у которых есть хотя бы один общий с ним салон; записи аудита, все салоны которых ему доступны.
- Ограничение области применяется до поиска, OR-условий и пагинации (`App\Services\AccessScope`).
- Каждая форма проверяет права в `FormRequest::authorize()` до валидации, поэтому прямой запрос к чужому объекту
  получает 403. Связи (`role_ids`, `showroom_ids`, `department_ids`, `showroom_id`) перепроверяются на сервере.
- Нельзя: выдать роль, права которой есть не у вас; расширить доступ за пределы своих салонов; изменить свои роли,
  салоны, отделы, статус или глобальный доступ; отключить или лишить прав последнего активного администратора.
  Последнее защищено транзакцией с блокировкой строки роли администратора (`App\Services\AdministratorGuard`).
- Назначения вне зоны доступа редактора не показываются и сохраняются без изменений.
- Бизнес-код не проверяет числовой `role_id`, только имена прав.

### Аудит

Записываются: создание и изменение сотрудника, активация и отключение, установка пароля (без значения),
изменения ролей, салонов, отделов, выдача и отзыв глобального доступа, создание, изменение и удаление ролей,
изменения салонов и отделов, источников, справочников источников и подключений. Пароли, токены, cookie и
секреты (`secrets`, `api_key`, `api_salt`) вырезаются рекурсивно до записи; для секретов пишется только факт
«задан/заменён/удалён». Записи без салонов (роли, глобальный доступ, справочники) видны только пользователям с
глобальным доступом.

### Первый администратор

Фиксированного пароля в сидерах нет, сидеры не создают учётных записей.

```powershell
php artisan db:seed --force                           # роли, права, общий колл-центр (повторный запуск безопасен)
php artisan app:create-admin --name="Имя" --email=admin@example.com   # пароль запрашивается скрыто, дважды
# или явное повышение одной существующей учётной записи (с подтверждением):
php artisan app:promote-admin <email администратора>
```

Требования к паролю администратора в CLI: от 12 символов, буквы в разном регистре и цифры.

### Исправление: у администратора нет кнопок «Добавить салон» / «Добавить отдел»

**Точная причина — данные учётной записи, а не код.** Учётная запись #1 `<email администратора>` (единственная активная
сессия в рабочей БД `mangov2`) имела роль `administrator` и все 11 прав (`can('showrooms.manage')` и
`can('departments.manage')` = true, кэш Spatie актуален, имена прав на сервере и в React совпадают), но
`users.has_global_access = false`. Значит, `AccessScope::isGlobal()` = false, полноценных администраторов
(`AdministratorGuard::count()`) было 0, салонов за пользователем не закреплено. Роль была выдана в обход приложения:
`audit_logs` был пуст, а `app:create-admin`, `app:promote-admin` и экран сотрудника всегда пишут аудит и выставляют
глобальный доступ.

- «Автосалоны»: `ShowroomPolicy::create` требует `showrooms.manage` **и** глобальный доступ → `can.create = false`
  → кнопки нет.
- «Отделы»: общий отдел (`createIn(null)`) требует глобальный доступ → `can.createShared = false`; доступных
  активных салонов нет → в React `canCreateAny = false` → кнопки нет.

Политики, контроллеры, shared props (`auth.permissions`, `auth.globalAccess`) и условия в React работают по
задуманной модели: создавать салоны и общие отделы может только сотрудник с глобальным доступом. Ослаблять это не
нужно.

**Исправление данных** (штатный механизм, затронута только запись #1, роли и права ролей не менялись):

```powershell
php artisan app:promote-admin <email администратора> --force   # exit 0
```

После выполнения: `has_global_access = true`, `isGlobal = true`, полноценных администраторов 1. В аудите одна запись
`user.global_access_granted`. Роль уже была назначена, поэтому записи о смене ролей нет.

**Исправление кода:** не потребовалось. Добавлен регрессионный тест `tests/Feature/Organization/CreationAccessTest.php`:

### Автоматические технические коды салонов и отделов

Пользователь больше не придумывает `code`: при создании его генерирует сервер.

- **Схема не менялась**, применённые миграции не переписывались. Уникальность уже обеспечена индексами MySQL:
  `showrooms_code_unique` (все салоны) и `departments_scope_key_code_unique` (`scope_key = ifnull(showroom_id, 0)`:
  в пределах салона, общие отделы — среди общих). Длина поля — 50 символов.
- **Генерация** (`app/Support/CodeGenerator.php`): `Str::slug($name, '-', 'ru')`. Это транслитерация, нижний
  регистр и разделитель «-»; остаются `[a-z0-9-]`, `_` превращается в `-`. Результат обрезается до 50 символов.
  Если основа пустая (например «!!! ###» или иероглифы), используется `showroom` / `department`. При совпадении
  добавляется `-2`, `-3`, …; основа укорачивается так, чтобы код с суффиксом укладывался в 50 символов.
- **Выбор свободного кода** (`OrganizationManager::createShowroom/createDepartment`): одним запросом читаются
  все коды области с общим префиксом, включая неактивные записи, и берётся первый свободный вариант. Это не
  окончательная проверка: при одновременном создании два процесса могут выбрать один код. Тогда уникальный индекс
  отклоняет вставку, и создание повторяется в новой транзакции (до 5 попыток). Повтор срабатывает только при
  нарушении именно индекса кода, другие ошибки пробрасываются. После 5 неудач возвращается ошибка поля «Название»:
  «Не удалось подобрать уникальный технический код. Повторите сохранение.»
- **Запросы**: `code` запрещён (`prohibited`) при создании и редактировании салона и отдела. Подменённый запрос
  получает ошибку «Технический код создаётся автоматически и не может быть задан или изменён.», запись не меняется.
  Переименование меняет только название, код остаётся прежним. Права, области доступа, аудит (`code` пишется в
  событие создания) и `lock_version` не менялись.
- **Перенос отдела между салонами не поддерживается** (так было и раньше: при редактировании меняется только
  название). Теперь `showroom_id` в запросе редактирования явно отклоняется: «Перенос отдела в другой салон не
  поддерживается.» Поэтому конфликт кода при переносе невозможен, а код при переносе не меняется.
- **Существующие коды** (включая `call_center` из сидера и коды с `_` или заглавными буквами) не пересчитываются
  и не меняются; сидер по-прежнему ищет колл-центр по `call_center`.
- **Интерфейс**: в диалогах создания поля «Код» нет. При редактировании под формой есть сворачиваемый блок
  «Дополнительно» (`Collapsible` и `FormField` проекта, `components/organization/technical-code.tsx`) с
  полем «Технический код» только для чтения и пояснением «Технический код создан автоматически и используется
  для интеграций». В таблицах код по-прежнему показан под названием, поиск по коду работает.

Тесты (MySQL `mangov2_test`):
