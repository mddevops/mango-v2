# CRM V2 — предварительный план этапов

**Этот план не разрешает автоматическое выполнение этапов. Каждый следующий этап начинается только по отдельному
заданию пользователя.**

- Требования — в [PROJECT_SPEC.md](PROJECT_SPEC.md), фактическое состояние — в
  [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md).
- Порядок этапов с 4-го построен по рекомендуемой последовательности аудита старой CRM
  ([analysis/LEGACY_CRM_AUDIT.md](analysis/LEGACY_CRM_AUDIT.md), раздел 18), направление которого пользователь
  одобрил 20.10.2026.
- План предварительный: состав и порядок этапов уточняются пользователем. Модель таблиц и API будущих этапов здесь
  не задаётся — она проектируется в начале каждого этапа. Названия таблиц из аудита — концепция, не решение.
- Перед реализацией бизнес-модуля сверяется соответствующая часть аудита и старой CRM, а открытые вопросы из
  PROJECT_SPEC.md, относящиеся к этапу, согласуются с пользователем.
- **Настройка подключения и работающая интеграция — разные результаты.** Сохранённые параметры подключения
  получают статус «настройка сохранена». Интеграция считается работающей только после реализации адаптера и
  сквозной проверки на тестовом аккаунте или реальных обезличенных сообщениях.
- **Архитектура интеграций (решение пользователя, 20.10.2026):** одно ядро обработки обращений; общий API для сайтов,
  работающих в нашем формате; отдельные адаптеры для протоколов, которые от него отличаются. Универсальный
  конструктор интеграций (редактор URL, HTTP-методов, JSON-mapping, пагинации, исполняемых преобразований) сейчас не
  делается. Первый рабочий сценарий — сайт через общий API (этап 8), затем прямые звонки Mango VPBX (этап 9).
  Остальные протоколы и поставщики добавляются отдельными адаптерами по отдельным заданиям.

- **Ближайший объём (окончательное решение пользователя, 21.10.2026):**
    - расчётный день только у салона (этап 5);
    - клиенты, заявки, история и права (этап 6);
    - графики и распределение (этап 7);
    - обратный звонок через API сайта (этап 8);
    - прямой звонок через Mango VPBX (этап 9).

  Victory, чат, боты, партнёры, остальные интеграции, склад и отчёты сейчас не реализуются. Этапы 10–12 в
  ближайший объём не входят. Этап 13 начинается по отдельному решению. Существующие справочники не удаляются.

**Статусы:** `NOT_STARTED`, `IN_PROGRESS`, `READY_FOR_REVIEW`, `ACCEPTED`, `BLOCKED`.
`ACCEPTED` ставится только после явного подтверждения ручной приёмки пользователем; зелёные автоматические проверки
для этого недостаточны.

## 1. Существующая основа приложения

- **Цель:** рабочий каркас для следующих этапов.
- **Состав:** Laravel + Inertia + React + TypeScript; вход через Fortify (сброс пароля, двухфакторная
  аутентификация, регистрация отключена); sidebar-навигация; компоненты shadcn и ReUI; русская локализация; страницы
  ошибок; проверки `php artisan test`, Pint, PHPStan, `npm run check`, `npm run types:check`, сборка, Playwright.
- **Зависимости:** нет.
- **Ручная приёмка:** вход и выход, сброс пароля, навигация на десктопе и планшете, русский интерфейс, страницы
  ошибок.
- **Статус:** `READY_FOR_REVIEW`. Основа используется и по указанию пользователя сохраняется без переделки; явного
  подтверждения ручной приёмки этапа в истории не зафиксировано.

## 2. Структура организации и доступы

- **Цель:** салоны, отделы, сотрудники, роли и права с серверной проверкой действий и области доступа; аудит.
- **Состав:** реализован (см. IMPLEMENTATION_STATUS.md): салоны и отделы с автоматическими кодами, сотрудники с
  салонами, отделами и глобальным доступом, роли и права, защита последнего администратора, аудит, CLI первого
  администратора.
- **Зависимости:** этап 1.
- **Ручная приёмка:** под администратором создать и изменить салон и отдел без ввода кода; создать сотрудника с
  ролью, салоном и отделом; войти им и убедиться, что видны только его данные; проверить, что последнего
  администратора нельзя отключить; просмотреть аудит.
- **Статус:** `READY_FOR_REVIEW`. После отчётов об успешных проверках пользователь сообщал о замечаниях
  (не было кнопок создания, обязательный ручной ввод кода, часовые пояса, вид диалогов); они исправлены, повторная
  ручная приёмка пользователем не подтверждена. Открытые вопросы этапа — область доступа колл-центра и
  редактируемость типов отделов (PROJECT_SPEC.md, раздел 12).

- **Цель:** реестр сайтов с привязкой к салону и общие справочники типов сайтов и агентств.
- **Состав:** реализован до аудита (см. IMPLEMENTATION_STATUS.md): типы сайтов (начальные: Реклама, SEO,
  Реклама/SEO, Классифайд, VA), агентства, сайты (название, салон, тип, агентство, URL, примечание, активность);
  включение и отключение без удаления; права просмотра и управления; область доступа по салонам; аудит.
- **Место в плане:** частная реализация, которая в этапе 4 расширена до универсальных источников без потери данных
  (страницы «Сайты», «Типы сайтов», «Агентства» заменены разделами «Источники» и «Справочники источников», старые
  адреса перенаправляют). Проверенное поведение (область доступа, отключённые связанные записи, конфликты, аудит)
  перешло в этап 4.
- **Зависимости:** этап 2; анализ старой CRM.
- **Ручная приёмка:** создать агентство и тип сайта, создать, изменить, отключить и включить сайт; отключённые
  тип или агентство остаются у существующего сайта; сотрудник одного салона видит только сайты своего салона.
- **Статус:** `READY_FOR_REVIEW`.

## 4. Источники и настройки подключений

- **Цель:** универсальный раздел «Источники» вместо реестра только сайтов, справочники, на которые опираются
  обращения, распределение и отчёты (PROJECT_SPEC.md, раздел 5), и сохранение настроек двух первых подключений.
- **Состав (реализован 20.10.2026, см. IMPLEMENTATION_STATUS.md):**
    - сайты расширены до источников на месте (новыми миграциями, без пересоздания записей): название, один салон,
      вид, необязательная классификация, необязательное агентство, необязательный адрес, несколько каналов
      обращения, примечание, активность, технический код, созданный сервером;
    - справочники видов (Сайт, Квиз, Бот, Соцсеть, Классифайд, Партнёр, Ручной ввод), классификаций (Реклама, SEO,
      Реклама/SEO, VA), каналов обращения (Обратный звонок, Прямой звонок, Чат) и агентств:
      создание, переименование, порядок, отключение и включение без физического удаления;
    - редактируемые правила вида: разрешённые классификации и каналы, проверяемые сервером;
    - подключение «Приём заявок с сайта» — только привязка источника к будущему общему API и активность; адрес
      приёма и ключи не выдаются;
    - подключение «Mango VPBX» — учётная запись (название, API key и API salt в зашифрованном виде, разрешённые
      салоны, активность), привязка источников и их линий (телефон или SIP); состояние «Не проверено»;
    - управление подключениями и секретами — только полный администратор через отдельные права; область доступа по
      салонам; защита от одновременного редактирования; аудит без значений секретов; перенаправления со старых
      адресов.
- **Не входит:** приём заявок, вебхуков и импортов; проверка подключений запросом во внешнюю систему; универсальный
  редактор интеграций; Mango Calltracking и Calltouch (отложены); клиенты, обращения, распределение, граница
  расчётного дня, Excel, чат; общий источник с маршрутизацией между салонами; перенос данных старой CRM.
- **Зависимости:** этапы 2–3; аудит старой CRM; решения пользователя от 20.10.2026 (состав этапа и архитектура
  интеграций).
- **Критерии приёмки:**
    - администратор создаёт вид, классификацию, канал и агентство, меняет порядок, отключает и включает их;
      физического удаления нет;
    - источник вида «Сайт» и источник вида «Бот» без адреса и классификации создаются в одном разделе;
      недопустимое сочетание вида, классификации или канала отклоняется сервером с понятной ошибкой;
    - существующие сайты после перехода видны как источники с прежними ID, салоном, классификацией, агентством,
      адресом, примечанием и активностью; записи аудита сохранены; старые адреса страниц перенаправляют на новые;
    - сохранённое подключение отображается со статусом «Не проверено»; значение секрета после сохранения не
      показывается и отсутствует в ответах страницы, журналах и аудите; пустое поле сохраняет прежнее значение,
      замена и удаление выполняются явно;
    - одна учётная запись Mango обслуживает несколько источников и салонов; одну линию нельзя привязать дважды в
      одном аккаунте; одинаковый номер в разных аккаунтах допустим; SIP хранится строкой;
    - отключённые значения справочников остаются у существующих источников и не подменяются при редактировании;
      новым источникам их выбрать нельзя;
    - сотрудник одного салона видит и меняет только источники своего салона, в том числе при подстановке id;
      менять общие справочники без права и глобального доступа нельзя; подключения доступны только полному
      администратору;
    - конфликт одновременного редактирования показывается понятным сообщением;
    - серверные тесты, Pint, PHPStan, `npm run check`, `npm run types:check`, сборка и браузерный сценарий
      выполнены на тестовой базе.
- **Статус:** `READY_FOR_REVIEW`. Этап 3 вошёл в этот этап: его ручная приёмка выполняется по сценарию этапа 4.

## 5. Граница расчётного дня салона

- **Цель:** настраиваемая граница расчётного дня каждого салона с учётом его часового пояса.
- **Согласованный состав (окончательное решение 21.10.2026, PROJECT_SPEC.md, раздел 7):** только салон —
  часовой пояс (по умолчанию Europe/Moscow), включаемая граница (по умолчанию 19:00), при отключении календарные
  сутки; дата периода — дата его окончания; начало включительно, конец исключительно; граница 00:00 равна
  календарным суткам; выбор времени — ReUI `c-time-picker-9`; без исключений по id. Настройки у источников, видов
  источников и отделов не нужны.
- **Реализовано в коде (21.10.2026):**
    - в форме салона блок «Расчётный день» с ReUI Time Picker;
    - один серверный сервис расчёта по переданному моменту, календарной арифметикой в поясе салона;
    - миграция без сброса данных;
    - серверная проверка, права и область доступа, аудит, защита от одновременного редактирования.
- **Приведено к решению (21.10.2026):** режим расчётного дня у источника убран из формы, запросов, ответов и
  расчёта, источник всегда использует правило салона. Колонки `sources.business_day_mode`,
  `sources.business_day_boundary` и их CHECK-ограничение остались в БД неиспользуемыми, чтобы не удалять сохранённые
  значения.
- **Не входит:** обращения, очереди, графики, группы распределения, правила выбора оператора, API и вебхуки
  (этапы 6–8); переопределения у источников, видов, отделов и по классификации.
- **Зависимости:** этап 4; решение пользователя от 21.10.2026 (вопрос 13 PROJECT_SPEC.md).
- **Ручная приёмка (по согласованному составу):** изменить границу салона через выбор времени и отключить её;
  проверить значения по умолчанию у нового салона; сотрудник без права управления салонами не может изменить
  настройки салона; в форме источника настроек расчётного дня нет.
- **Статус:** `ACCEPTED` — пользователь проверил и принял этап 22.10.2026.

## 5а. Справочники заявок

- **Цель:** справочники, которые понадобятся заявкам этапа 6, — заранее и без самих заявок.
- **Состав (решение пользователя 22.10.2026, PROJECT_SPEC.md, раздел 6):**
    - общий раздел «Справочники» с меню раздела: статусы заявок, причины корзины, причины отказа / срыва и
      существующие справочники источников (их адреса сохранены);
    - статусы: код от сервера, название, описание, цвет из палитры, порядок, активность; ровно один активный
      начальный статус (по умолчанию «Новая»), атомарная смена; требования — дата перезвона, дата приезда, причина
      из выбранного справочника;
    - причины корзины и причины отказа / срыва — отдельные справочники: обязательный комментарий, область
      применения (все или выбранные салоны V2);
    - начальные данные из старых `order_statuses`, `order_trashes`, `order_drops` повторяемым сидером без старых

      `order_references.manage`; аудит до и после; `lock_version`;
    - начальный статус без обязательных требований; причины отказа / срыва без привязки к статусу (решения
      22.10.2026).
- **Реализовано в коде (22.10.2026):** всё перечисленное. Требования статусов применяются к заявкам с этапа 6.

  передачи, кредитное дело, чат, склад, результаты приезда (`order_arrivals`), аналоги `order_types` и
  `order_sources`, переходы между статусами.
- **Ручная приёмка:** см. IMPLEMENTATION_STATUS.md, раздел 4.
- **Статус:** `ACCEPTED` — пользователь проверил и принял подэтап 22.10.2026.

  графики, передачи, кредит, склад, отчёты, раздельный учёт звонков и покупок, способ оплаты, качество и
  изменение/удаление комментариев в это задание не входили и остаются в составе этапа и следующих этапов.
- **Будущее правило Mango (зафиксировано, не реализовано):** входящий звонок без подходящей заявки салона создаёт
  новую заявку; при наличии — привязывается к последней изменённой (`orders.updated_at`) подходящей заявке этого

  Таблиц звонков и Mango в этом задании нет.

- **Цель:** клиенты, фактические обращения и работа в конкретном салоне с историей и правами.
- **Состав:**
    - клиент и контакты: несколько телефонов повторяемыми полями, полный нормализованный номер с индексом;
    - каждое обращение отдельной записью с источником, каналом, временем и снимком атрибуции;
    - работа салона с ответственным и статусом;
    - правило заявок и звонков из раздела 6 PROJECT_SPEC.md: форма — новая заявка, повторная доставка — без дубля,
      звонок — в последнюю изменённую подходящую заявку салона без автоматического сброса результата;
    - индикатор повторов с мини-таблицей; повторные заявки и звонки считаются отдельно;
    - история на основе существующего аудита; звонки и комментарии — связанные записи; общая хронологическая
      лента в карточке;
    - отдельное право на просмотр истории и отдельное разрешение на межсалонный просмотр;
    - ручное создание и обработка; разделение способа оплаты, этапа, результата, причины и качества.
- **Зависимости:** этапы 4–5 и 5а (статусы, начальный статус, требования и причины применяются к заявкам здесь);
  ответы на оставшиеся части вопросов 16–18 и 20 PROJECT_SPEC.md.
- **Ручная приёмка:**
    - создать обращения одного клиента в разные салоны: история и повторы видны только в пределах салона, а
      межсалонная история — только при отдельном разрешении и в области доступа;
    - повторная отправка формы создаёт новую заявку со связью с историей салона;
    - повторная доставка того же запроса дубль не создаёт;
    - поиск идёт по полному номеру, включая дополнительные телефоны, а не по последним цифрам;
    - число обращений, заявок, звонков и покупок считается раздельно;
    - в ленте карточки видны создание, открытие полной и мини-карточки, изменения полей до и после, назначения,
      изменение и удаление комментариев с автором, временем и основанием системного действия;
    - фоновая загрузка и показ строки в списке просмотром не считаются;
    - без права на историю она недоступна и в интерфейсе, и прямым запросом, но действия сотрудника записываются;
    - действия администратора тоже записываются;
    - изменить или удалить запись аудита нельзя.
- **Статус:** `ACCEPTED` — пользователь проверил и принял задание 22.10.2026 (клиенты, заявки, история и
  ограничение видимости заявок); остальное из состава выше не начато.
